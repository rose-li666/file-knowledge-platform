# 原文件落盘与数据库提交之间的崩溃规则

本文件记录当前 M5/M6 已实现的写入和恢复规则；实际进程崩溃证据见 m5-report.md。

上传提交同一事务中的文件元数据与索引任务。正式文件已落盘但提交未确认时保留文件和意图，接口返回 UPLOAD_OUTCOME_UNCERTAIN，并要求先刷新列表核对，不自动重新上传。

## 写入顺序

1. 生成 documentId 和独立 storageKey；写入临时文件，计算大小与 SHA-256，执行 fsync。
2. 持久化上传意图清单，记录 documentId、storageKey、名称、大小、哈希和上传时间。新上传默认为未分类；清单与临时文件落盘后再继续。
3. 在同一持久化文件系统中将临时文件原子改名为正式文件；Linux 环境同步父目录。
4. 一个数据库事务提交文件元数据与索引任务。只有成功提交后才返回上传成功。
5. 删除意图清单并同步目录。清单清理失败不影响已经提交的上传结果。

## 启动对账

取得上传/恢复独占锁后、开放业务写入前执行，避免把正在上传的文件误认作孤儿。

- 正式文件存在且数据库无对应记录：即使有意图清单，也不自动宣称上传成功或生成可见文档。将文件及清单移动到 `/data/quarantine`，唯一文件名与清单保留人工核对依据；健康响应记录隔离原因。
- 数据库记录和正式文件都存在且一致：保留文档，清理遗留意图清单；对应任务已随事务提交。
- 数据库记录存在而文件缺失/哈希不符：保留记录，下载时实际核对大小和哈希并返回明确错误；残留清单异常在健康响应中报告，不能清除记录掩盖问题。
- 仅有临时文件或意图清单：记为未完成上传，在启动独占对账时隔离，无活动上传需要宽限期。
- 没有清单的正式文件：在独占对账下确认无数据库引用后隔离，禁止按文件名猜测归属。

隔离不是删除。原文件存储键唯一，隔离目标也使用唯一标识。禁止自动覆盖同名文件；跨目录移动保持在同一个 `/data` 文件系统。数据库与文件系统不具有联合事务，本方案通过意图清单、明确的成功边界和对账补偿收敛异常。

任务重启恢复、重复索引重试幂等和真实进程故障已在 M5 验证；M6 补充正文重试代次失效的竞态验证。
