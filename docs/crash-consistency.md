# 原文件落盘与数据库提交之间的崩溃规则

本文件是后续文件管理的实现契约，M1 不实现上传或恢复逻辑。

M2 已实现临时字节、SHA-256、fsync、持久化意图、原子改名、文件元数据提交及意图清理。索引任务尚未创建；启动对账、隔离恢复与故障注入仍留到 M5。正式文件已落盘但提交未确认时保留文件和意图，接口返回 UPLOAD_OUTCOME_UNCERTAIN，并要求先刷新列表核对，不自动重新上传。

## 写入顺序

1. 生成 documentId 和独立 storageKey；写入临时文件，计算大小与 SHA-256，执行 fsync。
2. 持久化上传意图清单，记录 documentId、storageKey、哈希和目标分类。清单不含密钥；清单与临时文件落盘后再继续。
3. 在同一持久化文件系统中将临时文件原子改名为正式文件；Linux 环境同步父目录。
4. 一个数据库事务提交文件元数据与索引任务。只有成功提交后才返回上传成功。
5. 删除意图清单并同步目录。清单清理失败不影响已经提交的上传结果。

## 启动对账

取得上传/恢复独占锁后、开放业务写入前执行，避免把正在上传的文件误认作孤儿。

- 正式文件存在且数据库无对应记录：即使有意图清单，也不自动宣称上传成功或生成可见文档。核对 documentId、storageKey 和哈希后，将文件及清单移动到 `/data/quarantine`，记录原因与处理时间，保留人工恢复依据。
- 数据库记录和正式文件都存在且一致：保留文档，清理遗留意图清单；对应任务已随事务提交。
- 数据库记录存在而文件缺失/哈希不符：保留记录并标记存储异常，下载返回明确错误；不能清除记录掩盖问题。
- 仅有临时文件或意图清单：记为未完成上传，按独立宽限期规则清理/隔离。
- 没有清单的正式文件：在独占对账下确认无数据库引用后隔离，禁止按文件名猜测归属。

隔离不是删除。原文件存储键唯一，隔离目标也使用唯一标识。禁止自动覆盖同名文件；跨目录移动保持在同一个 `/data` 文件系统。数据库与文件系统不具有联合事务，本方案通过意图清单、明确的成功边界和对账补偿收敛异常。

任务重启恢复、重复任务幂等和故障注入属于 M5；M1 不将这些设计标记为已验证。
